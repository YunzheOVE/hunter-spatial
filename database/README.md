# Panorama storage — Phases 1–3

The viewer is a Pannellum modal inside Hunter Spatial. SQLite holds metadata;
image bytes live in `local-data/uploads/`. Both are private filesystem storage,
outside Next's public assets, and `local-data/` is gitignored.

## Setup

Use Node.js **22.13 or newer** (built-in `node:sqlite` is required). From the
project root:

```powershell
npm install
npm run db:init
npm run db:seed
npm run dev
```

Initialization is also performed when opening the database. Re-running it preserves
records; it does not migrate existing tables after schema changes. Seeding is
explicit and repeatable: it copies the prototype example and inserts one approved
N304 record only if that fixture does not already exist. It does not approve or
replace other submissions.

Search **N304**, select it, and click **View in 360°**. The modal labels the seed
as a development example, **not a verified photo of N304**. Other locations display
"No panorama available." Close or press Escape to return to the same map state.

## Tables

See `schema.sql` for the exact schema reused from panorama-test:

- `users`: ID, name, unique case-insensitive email, password hash, uploader/reviewer
  role, and creation timestamp.
- `panoramas`: ID, location ID, relative file path, uploader, pending/approved/rejected
  status, horizontal/vertical coverage and vertical offset, upload timestamp,
  reviewer, and review timestamp.
- `sessions`: hash of an opaque session token, user ID, and expiry as Unix seconds.

Every database connection enables foreign keys. Locations are not duplicated into
a database table: the keys in `apps/web/public/data/routing-graph.json` are the source
of truth. Backend lookups validate against that list. Create a regular account
through **Upload → Sign up**, or use the precreated reviewer described below.
The reviewer account owns the seeded example image.

## Reviewer demo account

These are **shared local-demo credentials**:

| --- | --- |
| Email | `reviewer@login.cuny.edu` |
| Password | `ReviewerDemo2026!` |
| Role | `reviewer` |

Create the account from the project root:

```powershell
npm run db:seed
```

Sign in through **Upload → Sign in**, using the same form as regular users.
The database stores only a salted scrypt password hash. The address is reserved
from public registration; setup creates the reviewer if it does not exist. Repeated setup
preserves an established reviewer's password, including one changed locally.
Setup reports a conflict rather than promoting an uploader who already has the
reserved email. Approval controls remain Phase 4.

## Simple accounts and uploads

Sign up with a name of up to 50 characters, an `@login.cuny.edu` email of up to
100 characters, and a password of 8–100 characters.
Both users and reviewers use this exact domain, ignoring capitalization. Subdomains
and other domains are rejected for sign-up and sign-in.
Emails are case-insensitive and unique. New accounts always receive the uploader role;
reviewer self-registration is not supported. Passwords are one-way salted scrypt
hashes generated by Node's built-in crypto module, matching the seed hash format.
There is no JWT or external authentication service.

Sign-in creates a random session ID in an HTTP-only, SameSite=Lax cookie. SQLite
stores only the token's SHA-256 hash, user ID, and 24-hour expiry. Cookies are
Secure on HTTPS and work on HTTP for the local demo. Sign-out deletes the session
and clears the cookie; expired sessions cannot authorize requests. No email
verification or password reset is implemented in this MVP.

The Upload tab has a required location dropdown using the existing campus list,
with a search field to narrow its choices. Opening it from room details preselects
that location. Choose a JPEG, PNG, or WebP up to 20 MB and 64 megapixels, select
full spherical or partial coverage, optionally preview, then submit for review.
Images must decode correctly and cannot be animated. Sharp performs validation
only; the original image bytes and format are preserved. Locations, coverage,
and files are validated again on the server. File paths use generated names.

Every submission starts pending with its uploader derived from the session.
My submissions shows the current user's history and statuses, with private image
previews. No review decisions are available until Phase 4. Public map viewers
continue to use only approved images, so a pending upload cannot replace the
development seed or any previous approval.

## Account and submission endpoints

- `POST /api/auth/sign-up`: JSON `{name, email, password}`; creates an uploader and
  signs in. The reserved reviewer address returns 403; duplicate email returns
  409; invalid inputs or a domain other than `@login.cuny.edu` return 400.
- `POST /api/auth/sign-in`: JSON `{email, password}`; incorrect credentials return 401.
- `POST /api/auth/sign-out`: deletes the current session and clears its cookie.
- `GET /api/auth/session`: `{user}` with ID/name/email/role, or `{user: null}`.
- `POST /api/submissions`: authenticated multipart upload with `image`, `locationId`,
  `haov`, `vaov`, and `vOffset`; returns `{submission}` with status 201.
- `GET /api/submissions`: authenticated `{submissions: [...]}` for the current user.

Account endpoints return `{user}` and never return hashes. Submission metadata
includes location, status, timestamps, coverage, and image URL, never filesystem
paths. Missing login returns 401, invalid uploads return 400, and oversized
requests/files return 413. State-changing endpoints reject cross-origin browser
requests. All account and submission responses are uncached.

## Read endpoints

- `GET /api/panoramas?locationId=N304`: latest approved metadata or JSON `null`.
  Missing location ID returns 400; unknown ID returns 404. Metadata contains `id`,
  `locationId`, `imageUrl`, `haov`, `vaov`, `vOffset`, and `isDemo`, never a file path.
- `GET /api/panoramas/<id>/image`: approved images are public. Pending/rejected
  images are accessible only to their owner or a signed-in reviewer. Unauthorized
  access, missing files, unsupported extensions, invalid IDs, or paths outside
  uploads return 404. Metadata and images use `Cache-Control: no-store`.

Selection is by `reviewed_at DESC, id DESC`, not upload time. Older approved
records remain available. The modal fetches again each time it opens. Coverage is
in degrees: the prototype uses 270 / 90 / 0; full spherical imagery uses 360 / 180 / 0.

## Local operation

Run from the project root or `apps/web` using the Next.js Node server. This is not
a static export or a serverless storage setup. Stop the server and copy the whole
`local-data/` directory when backing up or moving the demo.

The committed `fixtures/example.webp` is copied from panorama-test's existing
example for reproducible local setup; it is not campus location evidence.
Reviewer decisions and runtime panorama badges/filtering are subsequent phases.
The existing static media catalog remains unchanged until the final map integration
phase. This local MVP has no registration email service or production hosting setup.
